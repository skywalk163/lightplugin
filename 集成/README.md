# lightplugin 集成层

把 74 个插件**真正挂进同一个 lightharness 工具注册表**，并给出模型可见的最终工具面。

## 它解决什么问题

插件各自单测全绿 ≠ 能共存。集成层专门验证三件单测覆盖不到的事：

1. **能否共存**：74 个插件在一个程序里 `导入` + `挂载`，会不会互相踩踏。
2. **工具名冲突**：`工具注册表` 是按工具名做键的字典，**同名会被静默覆盖**——
   单测（每个插件用独立注册表）发现不了，集成层逐个插件单独挂载再汇总才能查出来。
3. **能否执行**：挂进去的工具真的能被调到并返回正确结果（端到端冒烟）。

## 文件

| 文件 | 说明 |
|---|---|
| `生成全量挂载.py` | 生成器。扫描 `插件/` 下全部插件，产出下面两个产物（插件增删后重跑即可） |
| `全量挂载.light` | **生成物，勿手改**。导入并挂载全部插件，运行时报冲突与冒烟结果 |
| `工具总表.json` | **生成物**。每个插件注册了哪些工具（机器可读，供 lightharness 对接用） |

## 用法

```bash
cd G:/dswork/duan-light-merge

# 1) 重新生成（插件增删或改名后）
python lightplugin/集成/生成全量挂载.py

# 2) 跑集成冒烟（74 个插件挂载 + 冲突检测 + 端到端调用）
python lightplugin/运行.py 集成/全量挂载.light
```

生成时还会做一道**静态 schema 形状体检**（LP-D-017 防线）：扫描每个插件的 `.light`，
凡把 `properties` 写成空**列表** `[]`（而非空映射 `{}`）就点名行号（注释行不计）。
这是第 11 批一次性命中 15 处后加的门——注册成功、直接调 execute 也成功，只有宿主按 schema 造参时才炸。

## 判读输出

```
插件数=74                      # 参与挂载的插件数
各插件注册工具总数=154           # 逐个插件单独挂载后求和
工具名冲突数=0                 # >0 会逐条打印「哪个工具名被哪些插件重复注册」
统一注册表最终工具数=154         # 全部挂进同一注册表后的最终工具数
[ok] 统一挂载无同名覆盖         # 若 最终 < 求和，说明发生同名覆盖，会告警
端到端冒烟: 通过=5 / 失败=0
```

**关键不变量**：`统一注册表最终工具数 == 各插件注册工具总数`。
一旦前者变小，就是有插件的工具被同名覆盖掉了——模型会看不见那个能力。

## 端到端冒烟为什么只测 5 个工具

绝大多数插件的执行体依赖「注入式 executor」（真实网络 / 磁盘 / 进程由宿主注入）。
未注入时它们按设计**软失败**（返回 `isError=真` 并给出中文原因），这是预期行为，不是缺陷。

所以冒烟只挑 5 个**不注入也能正确工作**的纯逻辑工具做执行级证明：

| 工具 | 所属插件 | 验证点 |
|---|---|---|
| `风险判定` | 安全守卫策略 | 命令/路径/网址 三类风险分级 |
| `判定类型` | 类型运行时 | 值类型判定（整数） |
| `上下文装配` | 上下文装配裁剪 | 按预算装配（空块时软成功） |
| `合并字典` | 通用工具 | 字典合并 |
| `去重列表` | 通用工具 | 保序去重 |

要扩大冒烟范围，先在宿主侧注入对应 executor，再往 `生成全量挂载.py` 的冒烟段加用例。

## 与 lightharness 对接

`工具总表.json` 是给宿主用的清单：

```json
{ "plugin_count": 74,
  "plugins": { "存储抽象": { "tools": ["存储写入", "存储读取", ...], "tool_count": 4 }, ... },
  "tool_name_conflicts": {},       // 非空即需先改名再上线
  "total_tools_registered": 154,
  "empty_properties_list": {},     // 静态形状体检结果，非空即 schema 有隐形缺陷
  "empty_properties_list_count": 0 }
```

宿主侧按 `挂载(注册表)` 逐个调用即可（`挂载` 的额外参数都带默认值，统一用单参调用是安全的）。

# 宿主冒烟：把 154 个工具接进 lightharness 运行时

`全量挂载.light` 回答的是「**能不能挂进去**」，而 `宿主冒烟.light` 回答的是
「**挂进去之后，宿主运行时能不能正确调度它们**」。

差别在**走没走宿主流水线**：

| | 全量挂载.light | 宿主冒烟.light |
|---|---|---|
| 注册表 | lightharness 真 `工具注册表` | 同（真注册表） |
| 调用方式 | 直接取 `登记表[名]["execute"](参数)` | `注册表.执行(名字, 参数)` |
| 经过的阶段 | 只有 execute | 解析参数 → prepare → **JSON Schema 校验** → execute → finalize → 统计 |

**直接调 execute 会掩盖问题**——2026-09-28 首次跑宿主冒烟就当场抓出 3 个插件缺陷
（见下），这 3 个在各自单测和全量挂载里都是绿的。

## 用法

```bash
cd G:/dswork/duan-light-merge

python lightplugin/集成/生成宿主冒烟.py          # 生成（插件增删后重跑）
python lightplugin/运行.py 集成/宿主冒烟.light    # 跑宿主冒烟
```

## 六个阶段与判读

| 阶段 | 做什么 | 期望 |
|---|---|---|
| B | 模型可见描述表 `注册表.描述表()` 三要素体检 | 154 条，缺三要素 = 0 |
| C | schema 结构体检（object 型、有 properties、**且 properties 是映射**） | 坏 schema = 0 |
| D | 全覆盖派发：每个工具用**空参**走流水线 | 有必填的应被宿主拦下（PARAM_SCHEMA_INVALID） |
| E2 | 合法派发：按每个工具自己的 schema **造最小参数**再派发 | 执行成功尽可能多，schema 不符 = 0 |
| E | 定向用例：8 个纯逻辑工具给正确参数 | isError = 假 |
| F | 异常路径：调用不存在的工具 | `TOOL_NOT_FOUND` |

2026-09-28 第 11 批后实测（74 插件 / 154 工具）：

```
注册表工具数=154 / 描述表 154 条缺字段 0 / 坏 schema 0
[D]  空参派发 154 个：宿主校验拦下 118（缺必填）、可执行成功 36、其余失败 0
[E2] 合法派发 133 个：成功 131、schema 不符 0、待宿主注入 2、显式跳过 21
[E]  定向用例 8/8 通过      [F] 未知工具 → TOOL_NOT_FOUND ✅
断言通过=12 失败=0
```

（第 10 批时是 60 插件 / 100 工具，空参派发拦下 85、合法派发 79 成功 77。）

**E2 为什么是 133 而不是 154**：21 个工具会碰真实进程/网络/外部 API
（Python 脚本、SSH、终端、浏览器、图片/视频/三维生成、模型补全、网页抓取…）。
它们未注入时按设计软失败，但冒烟**不该赌「软失败一定生效」**，所以显式跳过并如实打印。
诚实 > 覆盖率。

## 宿主冒烟当场抓出的 3 个真缺陷（都是单测绿、直接调 execute 也绿）

| 工具 | 问题 | 后果 | 修法 |
|---|---|---|---|
| `判定类型`（类型运行时） | schema 把「值」声明成 `type: "string"`，但实现接受**任意类型** | 模型传 42 会被宿主判「参数校验失败」，工具永远调不通 | 改成 `oneOf` 互斥分支（number 已覆盖 integer，二者同列会让 42 命中 2 个分支） |
| `技能列表`（技能运行时） | `"properties": []` 写成空**列表** | 宿主按 schema 造参时炸在 `字典键列表(list)` | 改成空映射 `{}` |
| `人格列表`（身份人格装配） | 同上 | 同上 | 同上 |

### 第 11 批（2026-09-28）同一条缺陷又命中 15 处

第 11 批新写的 14 个插件里，有 8 个把 `properties` 写成了空列表（共 15 处）——因为照抄了旧样板。
宿主冒烟 C 阶段一次性全抓出来（**坏 schema 15 → 修完 0**），说明这道门有效；
但也说明「靠跑一遍才发现」不够，故在 `生成全量挂载.py` 加了**静态形状体检**（生成时即点名行号）。
顺带修掉 `MCP桥接.light` 里同一写法的一处**动态路径**残留（远端条目无 schema 时的兜底模式，
不在 `挂载` 里注册，所以 C 阶段扫不到，只有静态体检能发现）。

**结论**：插件单测必须补一条「走宿主流水线」的路径，只测 execute 是不够的。
这条已固化成本目录的 `宿主冒烟.light`。

## 一个光明语言坑（写冒烟脚本时踩到）

模块级计数器在段落里回写必须声明 `全局 X。`（全角句号），否则按 L-165/166 语义会
新建局部变量、模块级值永远不变，且**编译期只有警告、运行期才炸**
（`UnboundLocalError: cannot access local variable`）。冒烟脚本里的 `记通过` / `记失败`
已按此修正。
