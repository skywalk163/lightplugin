# MCP桥接 · 复刻任务卡

- **对标 dsh**：`packages/mcp`
- **能力**：Model Context Protocol 工具桥接：把远端 MCP 工具清单拉成本地可调工具
- **缺口核验**：完全无（mcp 0 命中）；lightharness 无 MCP 客户端
- **优先级**：P5　**批次**：第 7 批　**状态**：pending
- **依赖**：无
- **挂接契约**：`造工具定义(名字, 描述, 参数, 执行函数, ...)` + `工具注册表`；需宿主服务时用 `绳构造注册` / `绳装配`

## 复刻记录

- **挂接**：`造工具定义` → `工具注册表`；暴露 2 个工具：`MCP工具清单同步` / `MCP工具调用`。
- **验证**：`测试_MCP桥接.light` 7 组全过（挂载、清单同步逐条注册为本地工具、经同步工具委托、通用 MCP工具调用 委托、远端报错→isError、空清单反例、未配置 transport→isError）。
- **踩坑**：字符串里写 `{name,...}` 会被当作**插值**（LP-D-001）→ 描述文案改用「名字/描述/模式/执行体」规避花括号。
- **设计要点**：`MCP工具清单同步` 把清单条目自带的 `handler`（段落引用）直接注册为本地工具执行体，从而把远端工具清单转为本地可调用条目；`MCP工具调用` 为通用委托入口，经注入式 `远端口(工具名, 参数)` 执行。transport 约定返回 `{"ok":布尔,"结果":字符串,"原因":字符串}`，`ok==假` 即 `isError`。
- **横向补深（本批）**：新增 JSON-RPC 2.0 协议层（见上「已补」），全部为纯逻辑、零 IO、零网络；
  `测试_MCP桥接.light` 由 7 组扩到 20 组（新增 13 组，含信封/id 自增/pending 关联/error 归一/
  id 不匹配 / 未知 id / 空响应 / 缺 id / 单帧往返 / 粘包 / 半包 / 无 Content-Length 头 等正反例）。
  挂载契约 `挂载(注册表)` 与既有 2 个模型可见工具均未改动。
- **已知缺口（如实）**：
  - ✅ **已补（横向补深批）**：JSON-RPC 2.0 协议层 —— 信封装配 `造请求`（带自增 id）/ `造通知`（无 id）、
    响应解析 `解析响应`（result / error 分流，error 归一为 `"<code>: <message>"`，无 message 时仅 `"<code>"`）、
    id 关联（pending 表 `登记待答` / `取待答方法` / `清待答` / `待答数`，id 不匹配与未知 id 均判错）、
    stdio 纯逻辑分帧 `装帧` / `分帧` / `余帧` / `清缓冲`（按 `Content-Length: N\r\n\r\n` 切帧，支持粘包与半包）。
  - 仍缺：**协议层未与传输层接线** —— `MCP远端调用` 走的仍是宿主注入的 `远端口(工具名, 参数) -> {ok,结果,原因}`
    委托契约，没有改成「装配信封 → 装帧 → 发给 transport」。要接线需 transport 契约升级为收字节串，
    会影响现有下游调用方，故本批只补协议层、保持 `远端口` 契约不变。
  - 仍缺：真实 MCP **握手与能力协商**（`initialize` / `notifications/initialized` / capabilities 交换）未实现。
  - 仍缺：`分帧` 用 `长(负载)` 作为 Content-Length，那是**字符数而非字节数** —— 非 ASCII 负载（UTF-8 中文等）
    会算出偏小的长度。光明侧无已验证的「UTF-8 字节长度」内置，故如实保留此偏差。
  - 仍缺：未实现 `$/cancelRequest` 取消、JSON-RPC **批量请求**（数组信封）与进度通知。
  - 仍缺（沿用）：远端工具清单的 `schema` 直接透传，未做字段级校验或参数归一；handler 绑定远端名由调用方
    在清单条目的 handler 中固定（测试用 `假甲处理` 等各绑定一名）。
  - 仍缺（沿用）：`MCP工具清单同步` 为「注册即调用」语义，未实现远端清单的增量 diff / 版本号 / 撤销注册。
