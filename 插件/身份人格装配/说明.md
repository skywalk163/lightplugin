## 复刻记录

### 挂接方式

- `从 工具 导入 造工具定义, 造工具结果`；`从 内置核心字典 导入 字典键列表`
- `挂载(注册表)` 注册两个工具：**`人格列表`**、**`人格装配`**
- `人格装配` 参数 `名字` 支持 **`甲+乙` 多卡语法**（内部 `分割字符串(名字串, "+")`），可选 `任务`
- 纯逻辑插件，无外部依赖、无注入 provider

### 三个设计取舍

1. **装配与渲染分离**：先出「段表」（`["标题","正文"]` 列表），再 `渲染段表` 拼文本。
   宿主可只取部分段（例如只注入「边界」段），且段表天然可对接 `上下文装配裁剪` 插件。
2. **空段跳过**：基调/专长/禁忌/示例/任务为空时不产生段，避免系统提示出现 `专长: ` 这种空壳。
3. **人格冲突显式警告**：多卡基调不一致时**不静默取舍**，返回 `警告: 基调不一致: A / B`。
   基调沿用首位，专长/禁忌取**去重并集**。

### 验证结果

`测试_身份人格装配.light` **9 组（含 10 个断言小节）全部通过**，一次跑通、零返工：

登记与列举 / 取卡字段 / 未登记反例 / `含于`+`并入去重` / 装配分段空段跳过 /
单卡装配文本 / 多卡合并（专长 3 项去重并集） / 冲突检测 / 挂载端到端 / 软删除注销。

### 踩到的坑

- **列表与字典的成员方法不敢用**：仓内未验证列表是否有 `.包含`、字典是否有删除方法，
  因此手写 `含于(表, 值)` 与 `并入去重(目标, 来源)`；删除改为**置空软删除**（`注销人格`）。
  这是规避不是缺陷，但暴露了「可调用方法面不清晰」这一易用性问题，已入报错数据集。
- 唯一返工是自己数错段数（写成 4，实际 5），非语言问题。

### 已知缺口（如实，不谎报对齐度）

- **不对接真实系统提示注入链路**：本插件产出文本，由谁塞进 messages[0] 由宿主决定。
- **优先级语义弱**：多卡合并时基调"取首位"是顺序依赖，不是语义仲裁；
  真要做仲裁需要人格权重或任务相关性打分，本版未做。
- **冲突检测只看基调**：专长/禁忌冲突（如一张卡禁止给答案、另一张要求给答案）不检测。
- **无持久化**：人格卡只在内存，进程重启即失；真实 identity 包应有磁盘/配置来源。
- **软删除有副作用**：`注销人格` 置空后，`人格表.包含(名)` 仍为真（键还在），
  因此工具层额外判了一次 `== 空` 才报错——调用方若只用 `是否有效人格` 会得到错误结论。
